# DTCG 2025.10 Conformance Audit — `@tensor_1/tokens`

**Slice:** DTCG-1 (pure analysis — no token JSON or code was edited)
**Date:** 2026-07-03
**Branch:** `batch0-foundations`
**Scope:** every `$type` in use across `packages/tokens/tokens/base/*.json` + `packages/tokens/tokens/dark/*.json`

---

## 1. Pinned reference revision

This audit is measured against a single, explicitly pinned reference:

> **Design Tokens Community Group — Design Tokens Format Module, Editor's Draft, revision label `2025.10` (October 2025 draft of the DTCG format spec).**

All CONFORMANT / DEVIATION verdicts below are relative to that pinned revision. The DTCG format module is still an Editor's Draft (not a W3C Recommendation), so "DEVIATION" here means "diverges from the pinned 2025.10 draft's prescribed representation," not "invalid / broken." The relevant 2025.10 type definitions used as the yardstick:

- **`color`** — either a string (hex `#RRGGBB[AA]` etc.) or the structured color object `{ colorSpace, components, alpha, hex }`. Both string and object forms are tolerated by the 2025.10 draft.
- **`dimension`** — an object `{ "value": <number>, "unit": "px" | "rem" }`. **Not** a bare CSS string like `"4px"`.
- **`fontFamily`** — a single string **or an array of strings** (a font stack MUST be an array of individual family names).
- **`number`** — a JSON number (unitless). **Not** a quoted string.
- **`duration`** — an object `{ "value": <number>, "unit": "ms" | "s" }`. **Not** a bare CSS string like `"120ms"`.
- **`cubicBezier`** — an array of four numbers `[x1, y1, x2, y2]`. **Not** a CSS `cubic-bezier(...)` string.
- **`shadow`** — a composite object (or array of them) `{ color, offsetX, offsetY, blur, spread, inset }`, each sub-value itself typed (color as color, offsets/blur/spread as dimension). **Not** a bare CSS box-shadow string.
- **Aliases** — the reference form for one token referring to another is `"$value": "{group.token}"` (curly-brace path).
- **`$schema`** — the spec defines a top-level `$schema` hint but does not require it.

## 2. The load-bearing reason deviations are deliberate (`style-dictionary.config.mjs`)

Before classifying, the mechanism that makes most of these deviations **intentional and immovable** must be stated, because it changes the verdicts from "clean these up" to "must not touch."

### 2.1 The `uix/value` transform is the identity function

`packages/tokens/style-dictionary.config.mjs` registers a **value transform named `uix/value` that returns the authored `$value` verbatim** (lines 32–39):

```js
StyleDictionary.registerTransform({
  name: 'uix/value',
  type: 'value',
  transitive: true,
  // identity — preserve authored CSS verbatim.
  transform: (token) => token.original?.$value ?? token.$value ?? token.value,
});
```

The header comment (lines 10–15) states the intent explicitly:

> `uix/value — IDENTITY. Returns the authored $value untouched. This is what keeps the runtime tokens verbatim: --uix-accent: var(--uix-brand,#1447E6), --uix-brand-muted: color-mix(...). Static resolution here would silently kill every product's brand override. Do not "optimize" this away.`

The build pipeline runs **only two transforms** — `uix/name` and `uix/value` — and deliberately uses **no built-in `transformGroup`** (lines 44–48). There is no `css/color`, no `size/px`, no dimension/duration parsing anywhere. So whatever string sits in `$value` is emitted **byte-for-byte** into the generated `--uix-*` custom property (`decls()` at lines 63–64: `--${t.name}: ${val(t)};`).

**Consequence:** the "$value" strings are not just data — they are the exact right-hand side of a CSS declaration. `"120ms"`, `"cubic-bezier(.23,1,.32,1)"`, `"0 1px 2px rgba(0,0,0,.06)"`, `"\"Inter\",system-ui,sans-serif"` are all authored the way they must appear in CSS.

### 2.2 The runtime `var()` / `color-mix()` brand-override mechanism

Several color `$value`s are **not literals at all** — they are live CSS functions that must survive to the browser unresolved:

- `accent` = `"var(--uix-brand,#1447E6)"` — chains through the write-only `--uix-brand` slot so a product can retheme at runtime (`base/color.json` line 18, with `$description`: *"Must stay var() to keep live brand override."*).
- `accent-hover` = `"color-mix(in srgb, var(--uix-accent) 88%, #000000)"` — derived live from the accent (`base/color.json` line 21).
- `brand-muted` = `"color-mix(in srgb, var(--uix-accent) 12%, transparent)"` (line 25).
- `sev-4` = `"var(--uix-info)"`, `sev-5` = `"var(--uix-text-muted)"` — **cross-token references expressed as raw CSS `var()`, not DTCG `{alias}`** (lines 56–61).

If any of these were converted to a DTCG structured object or resolved statically, the identity transform would emit a *resolved* color and **the brand override would die silently for every downstream product.**

### 2.3 The parity gate freezes the exact output strings

`packages/tokens/scripts/check-parity.mjs` diffs the generated `build/css/tokens.css` against the frozen `packages/tokens/tests/tokens.baseline.css`. Its bar (script header + lines 45–47) is: *same selectors, same `--uix-*` names, and per-property `a[prop] !== b[prop]` value equality (whitespace-normalized).* The header calls out that the runtime tokens `var(--uix-brand,…)` / `color-mix(…)` **"must match exactly — that is the regression that would silently break every product's live brand override."**

Because the emitted value is the authored `$value` verbatim, **re-shaping any `$value` into a DTCG object would change the emitted CSS string and break parity** unless `tokens.baseline.css` were re-frozen in the same commit. That is the mechanical reason the DEVIATIONs below are tagged `must-not-change-parity`.

> **Terminology note.** `check-parity.mjs` normalizes whitespace before comparing, so parity is *semantic* (selector/name/value) rather than literal byte equality. This audit uses "byte-parity" as shorthand for that frozen-value contract; the operative constraint is that the authored `$value` string is the emitted CSS value and must not change without re-freezing the baseline.

## 4. Per-family classification (all 7 families end with an explicit verdict)

Verdict tags: **`keep-deliberate`** = an intentional design choice that we would keep even absent the parity constraint; **`migrate-later`** = conformant-ish or low-risk, could be tightened in a future DTCG-native pass; **`must-not-change-parity`** = changing it would alter the emitted CSS and break the frozen `tokens.baseline.css` / brand-override contract, so it is frozen until a deliberate re-baseline.

---

### 4.1 `color` — **CONFORMANT** (with a deliberate runtime-string extension)

- **Example (literal):** `base/color.json` → `bg-app` = `"#FAFAFA"`; `dark/color.json` → `border` = `"rgba(255,255,255,.08)"`.
- **Example (runtime):** `base/color.json` → `accent` = `"var(--uix-brand,#1447E6)"`; `accent-hover` = `"color-mix(in srgb, var(--uix-accent) 88%, #000000)"`; `sev-4` = `"var(--uix-info)"`.
- **Assessment vs 2025.10:** The 2025.10 draft accepts string color values, so hex / `rgba()` literals are **CONFORMANT**. The `var()` and `color-mix()` values are *not* colors the spec recognizes — they are live CSS functions. This is a deliberate extension, not the spec's "color" type, and (for the cross-token cases like `sev-4 = var(--uix-info)`) it stands in for what the spec would express as an alias. Kept as-is because it is the entire runtime brand-override mechanism (§2.2) and is frozen by parity (§2.3).
- **Verdict: `must-not-change-parity`** — the `var()`/`color-mix()` color strings feed the brand override verbatim; converting them to structured color objects or resolving aliases would kill the override and break the baseline. (Plain hex literals on their own are `keep-deliberate` / conformant, but the family as authored is dominated by the frozen runtime strings.)

---

### 4.2 `fontFamily` — **DEVIATION** (comma-string vs array)

- **Example:** `base/typography.json` → `font-sans` = `"\"Inter\",system-ui,sans-serif"` (also `font-heading`, `font-mono`).
- **Why it deviates:** 2025.10 requires a font stack to be an **array of strings** — `["Inter", "system-ui", "sans-serif"]`. These are authored as a single comma-joined CSS string.
- **Load-bearing reason:** the `uix/value` identity transform emits this string straight into `--uix-font-sans` and into the Tailwind `font` mappings (`twFonts`, config lines 85 & 108–109). CSS `font-family` wants exactly this comma-separated string; the baseline freezes it. An array would need a join step that does not exist in the pipeline, and would change the emitted value.
- **Verdict: `must-not-change-parity`** — the comma-string is the emitted CSS value; re-shaping to an array changes output and breaks parity. (A future DTCG-native build that authors arrays and joins them at emit time is possible → see the `migrate-later` note in §5, but as it stands today the value is frozen.)

---

### 4.3 `dimension` — **DEVIATION** (`"Npx"` / `"-0.02em"` / `"0"` string vs `{value, unit}`)

- **Examples:**
  - px string: `base/size.json` → `radius-sm` = `"8px"`; `base/space.json` → `space-1` = `"4px"`.
  - em string: `base/typography.json` → `tracking-tight` = `"-0.02em"`, `tracking-eyebrow` = `"0.06em"`.
  - unitless zero: `base/space.json` → `space-0` = `"0"`.
- **Why it deviates:** 2025.10 requires `dimension` to be the object `{ "value": 8, "unit": "px" }`. Three sub-issues: (a) bare CSS strings instead of the object; (b) `em` is **not** an allowed unit in the 2025.10 draft (only `px` / `rem`) — so `-0.02em` would be non-conformant even as an object; (c) `"0"` is a bare unitless string, and it is quoted (a JSON string) rather than the numeric `0` the object form implies.
- **Load-bearing reason:** identity transform → these strings become `--uix-radius-sm: 8px;`, `--uix-tracking-tight: -0.02em;`, `--uix-space-0: 0;` verbatim. `letter-spacing: -0.02em` and `letter-spacing: 0.06em` **need** the em unit — px would change the typographic result — so the "non-conformant unit" is a correctness requirement, not sloppiness. The `pxNum()` helper (config line 121) already derives unitless px numbers for the TS `num` export from these strings; the string is the source of truth. Baseline freezes every one.
- **Verdict: `must-not-change-parity`** — emitted CSS value equals the authored string; objectifying (or dropping `em`) would change output/behavior and break parity.

---

### 4.4 `number` — **DEVIATION** (quoted string vs JSON number)

- **Examples:** `base/effect.json` → `z-raised` = `"1"`, `z-toast` = `"100"` (z-index ladder); `base/typography.json` → `leading-body` = `"1.5"`, `leading-display` = `"1.05"` (unitless line-heights).
- **Why it deviates:** 2025.10 `number` is a JSON **number** (`1`, `1.5`), not a quoted string (`"1"`, `"1.5"`). The `$type` is correct; the value is the wrong JSON scalar type.
- **Load-bearing reason:** the identity transform reads `token.original.$value` and emits it verbatim — `--uix-z-raised: 1;`, `--uix-leading-body: 1.5;`. Authoring as a quoted string guarantees the emitted CSS token is exactly `1` / `1.5` with no numeric reformatting (e.g. no risk of `1.05` → `1.05` vs `1.0500`). The baseline is frozen against these exact strings.
- **Verdict: `must-not-change-parity`** — unquoting to a JSON number is a source change that (a) risks a serializer reformatting the emitted value and (b) must be co-committed with a re-baseline; it cannot land in an analysis-only slice and would break parity if done alone.

---

### 4.5 `duration` — **DEVIATION** (CSS `"Npx"`-style string vs `{value, unit}`)

- **Example:** `base/effect.json` → `dur-fast` = `"120ms"`, `dur` = `"160ms"`, `dur-slow` = `"240ms"`, `dur-slower` = `"320ms"`.
- **Why it deviates:** 2025.10 requires `duration` to be `{ "value": 120, "unit": "ms" }`. These are bare CSS `ms` strings.
- **Load-bearing reason:** identity transform → `--uix-dur-fast: 120ms;` verbatim; consumed directly as a `transition`/`animation` duration in component CSS. Baseline freezes it.
- **Verdict: `must-not-change-parity`** — the string is the emitted CSS value; objectifying it changes output and breaks parity.

---

### 4.6 `cubicBezier` — **DEVIATION** (CSS `cubic-bezier(...)` string vs `[x1,y1,x2,y2]`)

- **Example:** `base/effect.json` → `ease-out` = `"cubic-bezier(.23,1,.32,1)"`; also `ease-out-strong`, `ease-in`, `ease-in-out`, `ease-spring`.
- **Why it deviates:** 2025.10 requires the four-number array `[0.23, 1, 0.32, 1]`. These are authored as the full CSS `cubic-bezier(...)` function string.
- **Load-bearing reason:** identity transform → `--uix-ease-out: cubic-bezier(.23,1,.32,1);` verbatim; used directly as a `transition-timing-function`. The `[x1,y1,x2,y2]` array would need a wrap step (`cubic-bezier(${arr.join(',')})`) that the two-transform pipeline does not perform, and would change the emitted value. Baseline freezes the string.
- **Verdict: `must-not-change-parity`** — the CSS-function string is the emitted value; converting to the array changes output and breaks parity.

---

### 4.7 `shadow` — **DEVIATION** (CSS box-shadow string vs composite object)

- **Examples:** `base/effect.json` → `shadow-sm` = `"0 1px 2px rgba(0,0,0,.06)"`; `shadow-popover` = `"0 8px 24px rgba(0,0,0,.10),0 1px 2px rgba(0,0,0,.05)"` (a **two-layer, comma-separated** shadow); `highlight-top` = `"inset 0 1px 0 rgba(255,255,255,0)"` (an `inset` shadow); `dark/effect.json` → `highlight-top` = `"inset 0 1px 0 rgba(255,255,255,.04)"`.
- **Why it deviates:** 2025.10 requires `shadow` to be a **composite object** `{ color, offsetX, offsetY, blur, spread, inset }` (and an **array** of such objects for multi-layer shadows), with each sub-value itself DTCG-typed (color as `color`, offsets/blur/spread as `dimension`). These are authored as raw CSS `box-shadow` strings — including a multi-layer comma-joined string and `inset` keywords that the object form would encode as the `inset: true` flag.
- **Load-bearing reason:** identity transform → `--uix-shadow-popover: 0 8px 24px rgba(0,0,0,.10),0 1px 2px rgba(0,0,0,.05);` verbatim; dropped straight into `box-shadow`. Decomposing into the composite object (or array) would require a serializer to reassemble the exact string — including the two-layer comma join and `inset` — which the pipeline does not have, and any reassembly risks a different byte string. Baseline freezes it.
- **Verdict: `must-not-change-parity`** — the multi-layer CSS string is the emitted value; the composite-object form would need a reassembly step that doesn't exist and would break parity byte-for-byte.

---

### 4.8 Structural: `$schema` and aliases (context, not one of the 7 families)

- **`$schema` — DEVIATION (missing):** no file declares a top-level `$schema`. The 2025.10 draft defines `$schema` as an optional hint, so this is a soft deviation. It costs nothing at runtime (Style Dictionary ingests the files without it) and adding one touches no `$value`, so it does not affect parity. **Verdict: `migrate-later`** — safe to add in a future DTCG-native pass; deliberately out of scope for this analysis-only slice.
- **Aliases — DEVIATION (raw `var()` instead of `{alias}`):** cross-token references (`sev-4 = var(--uix-info)`, `sev-5 = var(--uix-text-muted)`, and the whole `var(--uix-brand,…)` brand chain) are expressed as raw CSS `var()` strings, not the DTCG `{group.token}` alias form. This is intentional: DTCG aliases resolve at **build** time, whereas `var()` resolves at **runtime in the browser**, which is exactly what the brand-override / dark-cascade mechanism needs (§2.2). **Verdict: `keep-deliberate`** — runtime `var()` chaining is a design requirement the DTCG alias form cannot satisfy; the brand ones are additionally `must-not-change-parity`.

**Bottom line:** exactly one of the seven value families (`color`) is materially CONFORMANT for its literal values; the other six deviate by design. Every deviation is a direct consequence of the `uix/value` **identity transform** (emit `$value` verbatim) plus the **runtime `var()`/`color-mix()` brand-override** requirement, and all six value-family deviations are frozen by the `check-parity.mjs` baseline — hence `must-not-change-parity`. A future DTCG-native migration (author objects/arrays, add serialization steps in the build, re-freeze `tokens.baseline.css` in the same reviewed commit) is the only conformant path; that is deliberately deferred (`migrate-later` for `$schema`; the value families would follow the same co-committed re-baseline discipline). Nothing here should be "cleaned up" opportunistically — doing so silently breaks the brand override for every downstream product.
