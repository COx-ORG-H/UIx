## Definition of Ready

### Problem and audience

UIx consumers need eleven domain-neutral authoring, scheduling, relationship, review, metric, branding, diff, and color capabilities that currently do not exist in the published CSS/React catalog. The audience is product engineers building enterprise workflows in TENSOR and other house products. UIx owns presentation, interaction, typed models, and accessibility; consuming products continue to own domain catalogs, persistence, permissions, and business rules.

### Non-goals

- Do not add `CartDrawer`.
- Do not modify TENSOR, its dependency ledger, or any sibling repository.
- Do not merge or rebase the unrelated `main` branch.
- Do not add persistence, product-specific fields/operators/actions/record types, permissions, or network calls.
- Do not add drag-to-reschedule, unbounded graph rendering, a general code editor, or a full design-tool color-management system.
- Do not publish packages or merge the pull request.
- Do not alter the `--uix-*` token contract unless implementation proves an existing token cannot express a required state. The current design expects no token changes.

### Acceptance criteria

The phase is done only when all eleven canonical deliverables below have framework-neutral CSS, a typed React export, a representative styleguide example, light/dark visual coverage, Playwright accessibility coverage, and focused tests for nontrivial model logic. Every interaction has a keyboard path, state is described independently of color, reduced motion is respected, empty/loading/error states are usable where applicable, generated outputs are fresh, the additive API report is intentional, and the linked minor changeset releases both packages together.

### Stack and architecture decision

- Keep the existing npm workspace, React 18/19 peer contract, per-file ESM output, bundled CJS entry, DTCG-generated token outputs, plain HTML/CSS/JS styleguide, Node test runner, and Playwright/axe gates.
- Implement interactive React surfaces as controlled-first components with optional local interaction state only where persistence is not implied (focus, expansion, temporary input text, selected rows).
- Put reusable transformations in framework-neutral TypeScript model modules. Components consume those helpers; Node unit tests import the same source modules.
- Add no runtime dependency. Calendar/time-zone work uses `Intl.DateTimeFormat`; diff/color/rule/graph/numeric logic is small internal code. Relationship graph layout is a deterministic bounded SVG model; see `Docs/adr/0001-relationship-graph-layout.md`.
- Add a dedicated `phase-46-9.html` showcase and `guide/phase-46-9.js`. This keeps the existing catalog navigable while giving the eleven dense capabilities one deterministic visual/a11y surface.
- No new DTCG token is proposed. Component CSS must use existing `--uix-*` values; component-intrinsic geometry may use contract-gate-approved numeric geometry.

### Top risks and early checks

1. **API breadth becomes shallow or product-specific.** Mitigation: finalize public prop models before interiors; keep descriptors/catalogs/callbacks consumer-supplied; add smoke-consumer type examples for all eleven exports.
2. **Dense widgets look accessible but lose keyboard/focus behavior.** Mitigation: explicit roving focus or native controls, live regions for bulk/validation feedback, list/agenda equivalents, and Playwright keyboard-path assertions in addition to axe.
3. **One giant phase bloats CSS/JS or destabilizes snapshots.** Mitigation: one CSS module and one React module per deliverable, pure helpers for deep logic, no new dependency, size evidence before/after, and a separate deterministic showcase page.
4. **UTC/time-zone and three-way diff edge cases produce incorrect models.** Mitigation: pure unit fixtures across date boundaries, DST-adjacent instants, and conflicting/one-sided changes before UI wiring.
5. **Local runtime differs from CI.** The untouched baseline was run on Node `v24.18.0` while repository policy pins Node 22. Build/parity/contract/API/performance passed; `test:smoke` encountered npm-prefixed JSON and `test:size:css` reported zlib-only drift with a clean git diff. Re-run on Node 22/CI and treat CI/Linux as authoritative; harden a gate only if it fails on the supported runtime or the hardening is narrowly compatible.

### Data, security, compliance, and production-readiness constraints

- Models must remain JSON-compatible and serializable; no hidden persistence or injected executable CSS.
- Render consumer text as React content or text nodes; never evaluate catalog values or diff content.
- Do not fetch, upload, store, or transmit record, schedule, graph, file, logo, or profile data. File selection remains a consumer callback/local preview concern.
- Components expose accessible states but do not implement authorization, tenancy, audit trails, or data residency; those stay with consumers.
- Dependency/supply-chain layer owner: this PR (zero new runtime dependencies, pack/size evidence).
- Accessibility and interaction layer owner: this PR (axe, keyboard tests, visual states).
- Observability, analytics, persistence, tenant isolation, backup/recovery, and operational alerting: deferred to consuming applications because UIx performs no I/O and owns no runtime service.

## Public API proposals

Names below are the intended additive surface. Exact supporting type names may be refined during typecheck, but changing component responsibilities requires updating this plan first.

### Release group A

1. **`RuleBuilder`** — controlled `value: RuleDefinition`, `onChange`, consumer-supplied `fields`, `operators`, `actions`, `maxDepth`, optional `validate`, `readOnly`, and summary renderers. Export JSON types (`JsonValue`, `RuleCondition`, `RuleGroup`, `RuleAction`, `RuleDefinition`) and catalog/editor contracts. Pure helpers cover validation, bounded insertion/removal/reordering, and readable summaries.
2. **`BuilderCanvas`** — controlled `items`, `onItemsChange`, `palette`, selection callbacks, `renderItem`, and `renderProperties`. Native drag is an enhancement; Add/Move up/Move down/Remove buttons are the canonical path. Selection moves focus to the property-panel heading without stealing focus on initial render.

### Release group B

3. **`SchedulingCalendar`** — controlled `view`, `anchorDate`, UTC ISO `entries`, `timeZone`, overlays, filters, selection/expansion callbacks, and labels. Export month/week/agenda view and entry/overlay state types. Multi-day entries become clipped inclusive date spans in the supplied IANA zone.
4. **`DateRangePicker`** — controlled `{ start, end }` ISO-date value, `onChange`, `visibleMonth`, optional min/max and `isDateDisabled`, two-month default, invalid state/message, and locale. Arrow keys, Home/End, PageUp/PageDown, Enter/Space operate the calendar grid; native text inputs are not required.
5. **`RelationshipGraph`** — typed nodes/edges, selected node, bounded `maxNodes`, density, highlighted/conflicted IDs, expansion and detail callbacks, optional consumer positions, and a visible equivalent list. Export deterministic layout/bounding helpers. Controls provide pan, zoom, reset, node traversal, neighbor expansion, and details without pointer dependency.

### Release group C

6. **`MatchReview`** — descriptor-driven incoming record and candidate records, confidence, controlled decisions, selection, accept/dismiss/split/pick-other and bulk callbacks. Announce bulk counts/results and expose pending/resolved states in text.
7. **`MetricInput`** — controlled numeric/null value, `onValueChange`, min/max/step, invalid state, unit label, parse/format hooks, and accessible increment/decrement controls. Reuse `Input` styling and stepper language; export clamp/step helpers rather than a second general numeric state engine.
8. **`LicensePositionBar`** — `consumed`, `entitled`, formatter/unit/labels, accessible summary, over-allocation overflow, and optional class name. Compose `Meter` and `StatusPill`; keep the public name canonical while wording stays capacity-versus-limit neutral.

### Release group D

9. **`BrandProfileEditor` plus `BrandProfile` / `applyBrandProfile`** — readable serializable model, controlled profile selection/editing, ColorPicker composition, native file-input callback, and live preview. `applyBrandProfile(profile, target?)` writes only existing `--uix-brand`, `--uix-brand-fg`, and explicitly supported existing typography metadata; it returns a cleanup/snapshot value and never creates accent/link/ring/muted overrides.
10. **`DiffViewer`** — accept base/current/incoming JSON data or precomputed entries, controlled per-path resolutions, expandable regions, group filters, summary counts, and resolution callbacks. Pure three-way flatten/classify logic identifies added/removed/changed/conflicted entries.
11. **`ColorPicker`** — controlled normalized hex value, configured foreground, preset/recent palettes, contrast threshold, popover label, and `onChange`. Hue/saturation/value controls and the hex field all reach the same value; the hex field is the complete keyboard path. Focus is trapped while open and restored to the swatch on close; contrast status is live and independent of color.

## Accessibility behavior

- Use native buttons, inputs, selects, details/summary, tables, lists, dialogs/popovers, meters, and SVG labelling before custom roles.
- Provide visible text for conflict, invalid, pending/resolved, over-limit, schedule state, graph edge/node state, and contrast pass/fail; color is redundant.
- Use `aria-live="polite"` for rule validation summaries, range selection, match bulk results, profile application, diff resolution counts, and contrast status.
- Use roving focus for calendar dates and graph nodes. Arrow-key behavior follows the relevant grid/tree convention; Tab enters/exits composite widgets once where practical.
- Builder reorder, rule reorder/group operations, graph pan/zoom/expand, diff resolution, and bulk review all have labelled buttons reachable by Tab.
- Calendar exposes agenda view as a first-class equivalent; graph renders an equivalent node/relationship list, not a visually-hidden afterthought.
- ColorPicker traps Tab only while its modal popover is open, supports Escape, closes on explicit action, and restores trigger focus.
- Motion is limited to existing transition tokens/classes and disabled under `prefers-reduced-motion`; focus uses the existing high-contrast `--uix-ring` contract.
- Empty/loading/error content includes a useful next step or retry callback when one exists.

## Dependency decisions

- **Relationship graph:** internal deterministic bounded layout. Cytoscape.js 3.34.2 is a full model/renderer package (~5.7 MB unpacked); d3-force 3.0.0 is smaller (~89.6 KB unpacked) and side-effect-free but adds three dependencies and a simulation/timer lifecycle. Neither is justified for a bounded UI component whose required interactions, accessible equivalent, and consumer-supplied positions still need custom code. See the ADR for sources, rejected alternatives, tree-shaking, and rollback triggers.
- **Calendar/time zones:** native `Intl.DateTimeFormat` with explicit IANA zone and ISO parsing; no date library.
- **Diff:** internal recursive JSON flattener/classifier; no syntax-highlighting or diff dependency.
- **Color:** internal RGB/HSV/hex normalization and WCAG relative-luminance math; no color dependency.
- **Rule/numeric models:** internal immutable helpers; reuse current Input/Meter/StatusPill/Button primitives.

## Release and changeset strategy

The phase is additive public CSS and React API, so both linked packages receive a **minor** changeset. No token-contract baseline change is expected. Generated package artifacts and API Extractor reports are committed per repository policy. Current package versions are `2.12.0`; `changeset version` is not run in this feature PR, so the planned release is `2.13.0` for both packages.

## Risks, rollback, and compensation

- Rollback is a normal revert of this additive PR before publication. No schema, data, or remote state migration exists.
- After publication, individual components can be deprecated and removed only under normal semver rules; public types and CSS selectors are therefore reviewed as durable contracts now.
- If bundle/interaction evidence later justifies a graph dependency, add it behind a separate optional entry point and supersede ADR-0001. Do not silently grow the main entry.
- If a new design token becomes unavoidable, stop implementation for that state, follow `Docs/contract-change-process.md`, edit DTCG source, update parity baseline, classify semver, and document the decision. Do not patch generated CSS.
- If Linux visual baselines cannot be generated locally, use the repository workflow/CI artifact; do not commit Windows images as authoritative goldens.
